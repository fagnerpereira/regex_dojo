# Linter choice: RuboCop vs Standard

Both are supported natively by `bundle gem --linter=rubocop|standard`.
Standard IS RuboCop under the hood — a curated, frozen ruleset with its own
`standardrb` executable. The choice is about configurability vs zero-bikeshedding.

## Choose Standard when
- Personal projects / small teams — no style debates, ever
- You want `standardrb --fix` and done
- You don't need rubocop-rspec / rubocop-rails style extensions enforced
  (Standard doesn't officially support RuboCop extensions in its config)

## Choose RuboCop when
- Team has existing style preferences to encode
- You want extensions: rubocop-rails, rubocop-rspec, rubocop-performance, rubocop-md
- Legacy codebase: `rubocop --auto-gen-config` creates `.rubocop_todo.yml`
  (allowlist of existing offenses — fix incrementally, new code stays clean)
- You want per-cop control (`Metrics/MethodLength: Max: 15`)

## Hybrid (best of both, common in gems)
Use RuboCop configured to inherit Standard's ruleset, then layer extensions:
```yaml
# .rubocop.yml
require:
  - standard
  - rubocop-rspec
  - rubocop-performance

inherit_gem:
  standard: config/base.yml

AllCops:
  NewCops: enable
  TargetRubyVersion: 3.1
```
Gemfile (development group):
```ruby
gem "standard"
gem "rubocop-rspec"
gem "rubocop-performance"
```

## Rakefile integration (both)
```ruby
# Standard — generated by bundle gem --linter=standard
require "standard/rake"
task default: %i[spec standard]

# RuboCop — generated by bundle gem --linter=rubocop
require "rubocop/rake_task"
RuboCop::RakeTask.new
task default: %i[spec rubocop]
```

## CI runs (faster: separate gemfile for lint-only job — Evil Martians technique)
```ruby
# gemfiles/rubocop.gemfile
source "https://rubygems.org"
gem "standard", "~> 1.0"
```
```bash
BUNDLE_GEMFILE=gemfiles/rubocop.gemfile bundle install
BUNDLE_GEMFILE=gemfiles/rubocop.gemfile bundle exec standardrb
```
